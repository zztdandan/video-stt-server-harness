## 2. E1 —— "跳过完全没有语音的片段"能不能省？

VAD（CPU 5.33s / GPU 2.28–5.72s，588K 参数）结果：

| 指标 | 值 |
|---|---|
| 语音占比 | **42.5%**（905.7s / 1800s） |
| 非语音间隙 | 533 段、合计 894.3s（49.7%） |
| 间隙长度分布 | ≥1s：243；≥5s：41；≥10s：7；≥30s：1；最长 **33.67s** |
| **30s 网格纯无语音片** | **0 / 60**（语音占比 <10% 的仅 2 片） |
| **180s 网格纯无语音片** | **0 / 10** |

**结论：在这部素材上收益为 0。** 近一半时长确实是非语音，但它以碎片形式散布（平均每段 1.7s），**没有任何一个切片是完全无语音的**，D6"纯静音片直接跳过"无从触发。只有当 `min_chunk_speech_ratio` 放宽到 >0（例如跳过 <10% 语音的片）才有 2/60 片可省——量级可忽略。

**副产物（重要否证）**：此前推测"~100s 慢批由纯非语音片触发"——本数据**不支持该假设**（无纯无语音片，慢批依然出现）。慢批成因仍**未知**，见 §6。

## 3. E2 —— 定点切能否更精确地切 <180s？

### 3.1 机制成立

| 项 | 值 |
|---|---|
| fallback 率 | **0%**（10/10 切点全部命中窗内"语音段结束点"） |
| 切点策略分布 | `vad_offset` ×10，无 `energy_min`/`hard_cut` |
| 切点处语音概率 | 均值 **0.054**、最大 0.197 |
| 到最近语音边界距离 | 中位 **0.00s**、最大 **0.00s** |

### 3.2 与官方能量切/固定网格对比（同一份 VAD 帧概率，VAD 走 CPU）

| 切点策略 | n | 切点处语音概率 均值/最大 | 到最近语音边界距离 中位/最大 |
|---|---|---|---|
| **VAD 定点切** | 10 | **0.054 / 0.197** | **0.00s / 0.00s** |
| 官方能量切（现行为） | 9 | 0.092 / 0.470 | 0.25s / 3.82s |
| 固定 180s 网格 | 9 | 0.346 / 0.976 | 0.54s / 2.62s |

→ **"更精确"成立**：能量切最坏会落在语音概率 0.47 的帧上、离真实边界 3.82s；固定网格最差（0.976 = 直接切在语音中间）。
→ **但"切点前后 ±1s 静音占比"这个指标没有判别力**（三者为 0.61 / 0.64 / 0.65，几乎相同），不应作为 handoff §4.4 的判据。

### 3.3 **方案缺陷（实测发现）**：handoff D2 的字面写法会切出 >180s 的片

| 锚定方式 | 片数 | 最长片 | **超 180s 片数** |
|---|---|---|---|
| `grid`（目标 = k×180，即 handoff 字面写法） | 10 | **182.14s** | **5 / 10** |
| `prev`（目标 = 上一刀 + 180） | 11 | **179.72s** | **0 / 10** |

原因：切点向前吸附后，下一片变成 `(cut_k → (k+1)×180)`，长度 = 180 + (180 − cut_k)。超限片会被包内 `split_audio_into_chunks` **二次切分**（`qwen3_asr.py:366`），VAD 定点被废弃——正是 handoff §3 想避免的后果。
**修法**：名义切点必须**锚定上一刀**（`t = prev_cut + 180`），不是固定网格。已在原型中实现并复测通过。

## 4. E3 —— batch 10 → 3 的显存与耗时（切点完全相同，只变并行度）

| 配置 | 批数 | 各批耗时(s) | 总耗时 | RTF | **峰值显存** | 字符 | 覆盖率 |
|---|---|---|---|---|---|---|---|
| VAD 切 / **batch=3** | 4 | 112.1 / 102.8 / 101.2 / 100.5 | **416.6s** | 0.231 | **8.99 GB** | 667 | 0.9914 |
| VAD 切 / **batch=10** | 2 | 142.5 / 1.7 | **144.1s** | 0.080 | **16.12 GB** | 634 | 0.9914 |

- **显存结论（用户判断正确）**：降到 3 线后峰值显存 **16.12 → 8.99 GB（−44%）**，脱离 16GB 卡上限的贴顶状态。
- **代价**：耗时 **2.9×**（416.6s vs 144.1s）。原因是"每批一次的最坏片生成税"约 100–142s，**批数决定总耗时**；batch 越小 → 批数越多 → 税越多次。
- 内容量几乎不变（667 vs 634 字符，差异属单次运行噪声），覆盖率同为 0.9914。

### 4.1 投影（**外推，未实测**）

2h 素材 = 40 个 180s 片：batch=10 → 4 批 × ~145s ≈ **10 分钟**；batch=3 → 14 批 × ~105s ≈ **25 分钟**。

## 6. 仍未验证 / 被否证的

- **被否证**：慢批 ≠ 纯非语音片（§2）。~100–142s/批的成因仍**未知**，最可能是重复生成打到 `max_new_tokens=2048`；判别探针（2048→64）**未跑**，建议列为 P0。
- **未验证**：Δ 取值（本轮固定 30s，fallback 率 0% 说明还有下探空间，例如 Δ=15s 是否仍为 0）；VAD 的 `speech_threshold` 敏感性；重叠去重与 `context` 续接的效果；跨片上下文损失。
- **未验证**：`merge_silence_frame`/`extend_speech_frame` 等 VAD 后处理参数对切点的影响（本轮全默认）。

## 7. 对 handoff 各条决策的评估结论

| 决策 | 评估 |
|---|---|
| D1 定点切（不逐句） | **成立**，且实测 fallback 0% |
| D2 搜索窗 `[180-Δ, 180]` 只向前 | **方向对，写法有缺陷**：必须锚定上一刀，否则 5/10 片超限（§3.3） |
| D3 选 FireRedVAD | **成立**：4.33s 跑完 30 分钟（GPU），依赖只 +4 包，切点精度显著优于能量切 |
| D4 fallback 链显式化 | **成立但本轮未被触发**（0% fallback）→ 需换更差素材才能验证其价值 |
| D5 切点取 offset | **成立**：切点全部精确落在语音段结束点（距离 0.00s） |
| D6 纯静音片跳过 | **在本素材收益为 0**（0/60、0/10），建议保留开关但默认不指望它省算力 |
| 待定：重叠去重 + context 续接升必做 | **暂无法判断**（需先知道慢批与丢字的真实成因） |

## 8. 对 SPEC 的修订建议

1. `chunk_seconds` 默认：由"30s"改为 **180s + VAD 定点切（锚定上一刀）**；batch 默认由 10 降为 **3**（显存 9GB 安全区），把耗时换稳定性。
2. `min_free_vram_gb`：按实测改为 **10.0**（batch=3 峰值 8.99GB，留余量）；不再写 6.0。
3. 新增"每批最坏片税"说明：总耗时 ≈ 批数 × 100–142s，作为超时预算依据（2h 素材 batch=3 → 25 分钟投影，`stt_qwen_timeout_sec` 仍取 5400s 有余量）。
4. 观测项：`fallback` 计数（本轮 0，必须保留以捕捉退化）、逐片语音占比、片长直方图、批耗时。
5. 判据删除"切点前后 ±1s 静音占比 ≥0.6"（无判别力），改为**切点处语音概率**与**到最近语音边界距离**。

对照：片 0–3（语音占比仅 0.18–0.39）却产出 187–381 字。→ **产出量与语音占比不相关，坍缩是模型侧行为**，并直接造成 12 个 30–115s 的无效超长段与片尾 34.7 分钟仅 38 字。

### 9.3 机理定位（三连判别探针，同源同段）

取坍缩片 6（1063.5–1243.5s，VAD 0.695）单独复跑：

| 探针 | 耗时 | 产出字符 | 结论 |
|---|---|---|---|
| 180s 单次（batch 1） | 85.9s | **1** | 可复现坍缩，非批次偶发 |
| 同段切 7×26s（batch 6） | 103.4s | **41** | **切片长度是触发因素**（41×） |
| 同段 180s，`max_new_tokens=64` | **3.73s** | 1 | 耗时与上限**线性相关** |
| 同段 180s，`max_new_tokens=512` | **21.69s** | 1 | 同上（≈17ms/token） |
| 同段 180s，`max_new_tokens=2048` | **85.9s** | 1 | 生成一路打到上限 |

→ **根因：模型在部分音频上进入退化生成，一路生成到 `max_new_tokens` 上限**（故每批 ~100s 的"税"就是 `上限 × 每 token 时间`），而解析后只剩 1 个字。这也解释了历史上所有"~100s 慢批"现象。

### 9.4 待修项（实测暴露）

1. **片长必须回到短切片**（30s 级）：同一音频 180s→1 字、26s→41 字；此前 ABF-391-U 的 30s 配置（61 片）只出现 2 次慢批，未坍缩。
2. **`max_new_tokens` 必须按片长收紧**（安全闸）：它直接决定退化时的耗时上限。
3. **SRT 需过既有时间戳清洗 helper**：本次绕过它，产生 12 个 30–115s 超长段（仓库已有单调/上限/零长清洗，stt_qwen 落地时必须复用）。
4. 依赖外部手段（重复惩罚等）需改包或下沉到自定义 generate——本轮未验证。

- 产物结构校验（三片全过）：最长段均 **30.00s**、>30s 段 **0**、时间轴单调、空文本 0；清洗 adjusted 8/606、25/736、13/471（最长原始 45.5s / **80.0s** / 54.2s）
- 切点策略：`vad_offset` 486 片、`vad_offset_extended` 3 片、**`hard_cut` 2 片**（CJOD，最长片正好 80.0s = 50+30，硬切上界被严格触达）；`align_missing` 0/1/0

### 与上一轮 ADN（30s±20s / batch 10）的时间对比

| 配置 | 音频 | 片数 | 批数 | 推理 | 每音频小时 | torch峰值显存 |

### 占用结论

torch 自报峰值 10.4–11.9GB，但**整卡口径峰值 15.7GB / 16.4GB**，余量仅约 0.7GB。batch 13 + 50–80s 片可行，但**必须独占**：与其它任务（如 whisper 阶段或其它会话的服务）并发时会 OOM。
